# Web Security Hub 設計書

[English version](../ARCHITECTURE.md) · [仕様書](SPECIFICATION.md) · [詳細設計書](DETAILED_DESIGN.md) · [画面設計書](SCREEN_DESIGN.md)

この文書は、仕様書の機能をどのような構成で実現するかを示します。個別の処理規則は詳細設計書、画面は画面設計書を参照してください。

## 1. 設計方針

| 方針 | 内容 |
|---|---|
| ローカル完結 | 診断・検証・保存はすべて利用者の端末で行う。結果を外部へ自動送信しない |
| 許可と範囲の固定 | 診断や送信の対象、経路、方法、回数、時間を、実行前に固定して許可する。範囲外は拒否する |
| 証拠主義 | 判定は、試行に結び付いた観測と、独立した規則で行う。件数や評価値、HTTP ステータスだけでは決めない |
| 判定と探索の分離 | 探索を導く評価値と、脆弱性の判定を分ける。評価値から違反や安全を確定しない |
| 決定論 | 同じ入力・設定・乱数 seed からは、同じ候補と順序を再現する。AI は決定論的な生成の代替にしない |
| 失敗を安全側に倒す | 正常対照の失敗、未計測、timeout、取消、ソースの変更は、「問題なし」ではなく「判定不能」または停止として扱う |
| 責務の分離 | 画面、通信、ユースケース、判定規則、保存を分け、判定規則は通信や保存に依存しない |
| 任意機能の分離 | AI・ZAP・モデルは既定で無効で、無効でも主要機能が完結する |

## 2. システム構成

```text
┌──────────────────────────────────────────────────────────────┐
│ 利用者の端末                                                  │
│                                                              │
│  ネイティブシェル(デスクトップ版)／ブラウザー(ソース版)      │
│        │  画面表示                                            │
│        ▼                                                      │
│  ローカルサーバー ── 画面配信・API・進捗配信                  │
│        │                                                      │
│        ├─ 診断機能群    巡回／テスト生成／再実行／DAST／SAST  │
│        ├─ 検証基盤      許可範囲・試行・証拠・判定・報告       │
│        │     ├─ 探索    遺伝的探索／固定ルール／比較           │
│        │     └─ 任意    言語モデルによる候補供給               │
│        ├─ VEX 機能      証拠・レビュー・承認・書き出し         │
│        └─ 保存層        サイト／セッション／非公開レポート     │
│                                                              │
│  診断ブラウザー（Playwright）   専用サンプルのサーバー         │
│  任意: ZAP／Java、Appium、言語モデルのサーバー（loopback）     │
└──────────────────────────────────────────────────────────────┘
        │ 診断対象への通信（許可した対象のみ）
        ▼
   許可した Web アプリケーション／ローカル API
```

## 3. 構成要素

### 3.1 層の責務

| 層 | 責務 |
|---|---|
| 画面 | 設定入力、進捗と結果の表示、取消、教材への導線。判定や保存は行わない |
| API | 要求の検証、認可、ユースケースの呼び出し、応答。診断の詳細や保存形式を直接扱わない |
| ユースケース | 生成、再実行、検証、探索、比較、VEX 作成といった一連の処理を順序立てる。通信手段や画面を知らない |
| 判定規則（ドメイン） | 許可範囲の判断、判定、評価、探索の演算、VEX の規則。通信・ファイル・画面に依存しない |
| アダプター | ブラウザー、HTTP、ファイル、ZAP、Appium、言語モデルなどの外部とのやり取りと、その後始末 |
| 保存 | サイト設定、セッション、レポート、ドラフトを、決められた場所へ、所有者だけが読める権限で保存する |

### 3.2 診断機能群

| 構成要素 | 役割 |
|---|---|
| 巡回・フォーム抽出 | 同一オリジンを巡回し、フォーム・入力欄・制約・安定したセレクターを取得する |
| 値生成・組合せ | 入力欄の制約から正常・境界・異常の候補値を決定論的に作り、ペアワイズで組み合わせる |
| テストコード生成・再実行 | ケースをテストコードにし、ベースラインと比較して実行する |
| シナリオ実行 | ログイン・操作列を、共通の実行器で再生する（テスト生成と動的診断で共用） |
| シナリオ記録・認証セッション | 人の操作を記録し、手動ログインの結果を保存する |
| 画面探索 | 破壊的でない操作を隔離したタブで試し、画面遷移を地図にする |
| 動的診断 | 収集した通信と画面を、パッシブ規則で検査する |
| ZAP 連携 | ZAP のプロキシと API を使い、警告をケースに対応付ける |
| 静的解析 | ローカルのソースを規則で検査し、個別の識別子と位置を付ける |
| 報告 | 結果を JSON・HTML・Markdown・SARIF で出力する |

### 3.3 検証基盤

検証基盤は、「許可した範囲だけに、正常対照つきで試行を送り、結び付いた証拠で判定する」ための共通の土台です。サンプル検証・ソース検証・遺伝的探索が同じ土台を使います。

| 構成要素 | 役割 |
|---|---|
| 許可範囲の登録 | 対象の origin とポート、経路、メソッド、フィールド、認証プロファイル、期限、試行数、並行数、ソースの場所を一つの「許可」にまとめ、範囲外・期限切れ・別プロファイルへの差し替えを拒否する |
| 試行の実行 | 試行ごとに独立した通信の文脈を作り、正常対照 → 候補の順に送る。リダイレクトは追わず、取消・期限・timeout で必ず後始末する |
| 計測と相関 | サーバー側の観測を、ジョブ・試行・seed・リクエスト・認証プロファイルの 5 つの識別子と、ソースの識別子（SHA-256）に結び付ける |
| 判定 | 業務上の独立した規則で、正常・遮断・到達を区別して判定する。HTTP ステータスだけで判定しない |
| ソース照合 | 試行の前後でソースの識別子を確認し、変更があれば証拠を採用しない |
| 受動証拠（任意） | 試行ごとの専用 ZAP セッションで受動警告を集め、5 つの識別子とメッセージで試行に結び付ける |
| 結果の保存 | 設定・候補・判定・証拠を、非公開のレポートとして保存する |

### 3.4 探索と比較

| 構成要素 | 役割 |
|---|---|
| 遺伝子と個体 | 型と値の語彙が決まったフィールドの組を「遺伝子」とし、系譜（親・演算）を持つ個体として扱う。通信先や認証は遺伝子に含めない |
| 世代の演算 | 選択、交叉、突然変異、エリートの引き継ぎ、重複の排除、多様性の維持 |
| 評価 | 有効な観測だけを評価値にし、欠測と 0 を区別する。評価値は順位付けの用途に限る |
| 探索の制御 | 世代・試行・時間・停滞・多様性・取消で止め、停止理由を記録する |
| 独立再現 | 見つかった候補を別のセッションで再実行し、独立した判定で確認する |
| 固定ルール | 結果から学習しない、決定論的な基線 |
| 比較 | 方式・状態・seed を揃えて実行し、測定値を集計する。環境要因の失敗は再試行し、無効なら集計から除く |

### 3.5 言語モデルによる候補供給（任意）

- モデルへ渡すのは、型付きの候補値と集計値だけ。URL・認証・ファイル・証拠・識別子は渡さない。
- 応答は、遺伝子ごとの許可値を定めた厳密なスキーマで検査する。不正・途中切れ・拒否・過大・重複した応答は実行せず、有限の再試行のあと、モデルなしの探索に戻る。
- 呼び出し回数・token・費用に上限を設け、呼び出しの前に確認する。候補の一部を置き換えるだけで、試行の上限は変わらない。
- 接続先は、この端末（loopback）が基本。外部への送信は、明示の許可と費用の上限が揃ったときに限る。

### 3.6 OpenVEX 機能

| 構成要素 | 役割 |
|---|---|
| 証拠の要約 | 保存済みのレポートから、再現・非再現・判定不能を再導出する。レビュー担当者は観測を選べない |
| 規則 | 状態ごとの必須項目と、証拠からは導けない状態の禁止を検査する |
| レビュー・承認 | 名前のある承認者が承認する。承認時に証拠を読み直し、承認後は固定する |
| 改訂 | 文書 ID を保ち、版を上げた新しいドラフトを作る |
| 書き出し | 承認済みのドラフトだけを OpenVEX 文書にする |

## 4. デスクトップ版の構成

- ネイティブシェルが、同梱のランタイムでローカルサーバーを起動し、その画面を表示する。Node.js の事前インストールは不要。
- サーバーは loopback だけで待ち受け、起動ごとに発行する秘密のトークンを持つ要求だけを受け付ける。
- アプリを閉じると、サーバーと、アプリが起動した補助プロセス（ZAP など）も終了する。親が異常終了した場合も、補助プロセスを回収する。
- 保存先は利用者専用のデータ領域。診断ブラウザー、ZAP、Java は利用者の操作で、検証済みの固定版を導入する。

## 5. 主要な処理の流れ

### 5.1 テスト生成と回帰

```text
サイト設定 → 巡回・フォーム抽出 → 候補値の生成 → ペアワイズ → ケース
        → テストコード・YAML・レポート → セッション保存
セッション → ベースライン記録 → 再実行（比較先を指定可）→ 差分・結果
```

### 5.2 動的診断と ZAP

```text
許可確認 → 巡回・シナリオ → 通信の収集 → パッシブ規則で検査 → 検出結果
          └─ ZAP 有効 → 通信をプロキシへ → 警告を取得 → ケースに対応付け
```

### 5.3 検証基盤の試行

```text
許可の登録 → 正常対照 → （成功）→ 候補 → 観測の取得 → 独立した判定 → 報告
                  └─（失敗）→ 候補は送らず停止
各試行の前後で、ソースの変更・取消・期限を確認する
```

### 5.4 遺伝的探索

```text
初期候補 → 評価（正常対照つき）→ 選択・交叉・突然変異 → 新しい候補のみ評価
        → 停止条件の判定 → 違反らしい候補 → 別セッションで独立再現 → 報告
（任意）モデルの候補が、GA の候補枠の一部を置き換える
```

### 5.5 OpenVEX

```text
検証レポート → 証拠の要約 → 状態の提案 → ステートメント → 承認（証拠の再確認）
            → 書き出し → （変更時）改訂版 → 版を上げて再承認
```

## 6. セキュリティー設計

| 観点 | 設計 |
|---|---|
| 信頼境界 | 画面と API は同一端末内。外部へ公開しない。信頼するのは、サーバー側で固定した許可範囲だけ |
| 認可 | 診断・送信・記録は、許可の確認を必須とする。検証機能は、セッションと同一オリジンを必須とし、本人のジョブだけを参照・取消できる |
| 秘密情報 | 資格情報は専用の秘密情報ファイルにだけ保存し、結果・レポート・ログへ出さない。パスワード入力は記録しない |
| 入力検証 | 外部から入る値は、型・長さ・語彙・未知の項目を検査してから使う。許可リストにない項目は拒否する |
| 送信の制御 | 送信先は許可した数値の loopback に限定し、リダイレクトを追わず、許可範囲外へは送らない。応答の読み取りには上限を設ける |
| モデル | 既定で無効。渡す情報を最小化し、応答を検証し、予算を超えない。スコープや権限を変更させない |
| ファイル提供 | 識別子を検証し、対象の範囲に限り、頻度を制限する。ファイルは書き込み先と読み取り先を分ける |
| 非公開保存 | 結果は所有者だけが読める権限で保存する。レポートはスクリプトを含まない形式にし、入力はエスケープする |
| 後始末 | 取消・期限・異常終了で、ブラウザー・補助プロセス・一時ファイルを回収する |

## 7. 保存の設計

```text
データ領域/
  sites/<サイト>/        サイト設定、秘密情報、シナリオ、データセット、セッション
  artifacts/
    static-scans/        静的解析の結果
    private/             検証・探索・比較・VEX の非公開レポート（所有者のみ）
```

- 非公開の領域は、作成時に権限を絞り、シンボリックリンクや想定外の場所を拒否する。
- レポートは一度に書き込み、途中の状態を公開しない（書き込み完了後に確定する）。
- 保存件数と大きさに上限を設ける。

## 8. 外部との連携

| 連携先 | 目的 | 有効にする条件 |
|---|---|---|
| Playwright | 診断ブラウザーの操作 | 常に使用（利用者が導入） |
| OWASP ZAP | 既存ルールによる検査、受動証拠 | 利用者が有効化・導入 |
| Appium | モバイルの操作 | ソース版で、サイト設定が iOS／Android |
| 言語モデルのサーバー | 候補の提案 | 利用者が設定。画面では loopback のみ |
| 外部 AI のコマンドラインツール | アサーション、結果のレビュー | サイトごと・実行ごとの明示許可 |

## 9. 設計上の制約

- 巡回だけで、SPA、SSO、多段ウィザード、権限別画面をすべて網羅することはできない。シナリオを併用する。
- ZAP の警告とケースの対応は、URL と識別ヘッダーに基づく。サーバー側のリダイレクトなどで一意に結び付かない場合がある。
- 静的解析は軽量な規則検査で、データフロー解析や依存関係の脆弱性検査の代替ではない。
- ソースだけの結果は、実行中のコードとの同一性を証明しないため、常に「調査中」として扱う。
- 有限の試行の結果は、安全の証明ではない。
